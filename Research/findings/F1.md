# F1 — Cloudflare Workers execution and platform limits

Research date/access date: 2026-09-22

## Findings

### 1. Workers can handle HTTP ingress and streaming, but CPU and memory are bounded.

- Claim: A Workers HTTP invocation has no hard wall-time limit while the client remains connected, but CPU time is limited to 10 ms on Free and 5 minutes on Paid, with a 30-second default on Paid. Memory is 128 MB per isolate.
- Evidence: Cloudflare's limits page distinguishes CPU time from duration, lists the plan limits, and states that an HTTP request has no hard duration limit while the client remains connected.
- URL: https://developers.cloudflare.com/workers/platform/limits/
- Source date: last updated 2026-09-05
- Confidence: high

### 2. Background work after a response is limited; durable work should be moved to Queues or Workflows.

- Claim: `ctx.waitUntil()` extends an HTTP invocation for at most 30 seconds after the response or disconnect. Cloudflare recommends sending work that cannot finish in that window to a Queue.
- Evidence: The Context API documentation explicitly states the 30-second limit and recommends Queues for reliable out-of-band work.
- URL: https://developers.cloudflare.com/workers/runtime-apis/context/
- Source date: last updated 2026-09-10
- Confidence: high

### 3. Cron, Queue consumers, and Durable Object alarms have 15-minute wall-time limits.

- Claim: Scheduled Workers, Queue consumers, and Durable Object alarm handlers are limited to 15 minutes per invocation; Durable Object RPC/HTTP and Workflow steps can remain active while the caller is connected.
- Evidence: The Workers limits table lists wall-time limits by invocation type.
- URL: https://developers.cloudflare.com/workers/platform/limits/
- Source date: last updated 2026-09-05
- Confidence: high

### 4. Workers AI can provide model inference at the edge, but it is not a general agent runtime.

- Claim: Workers AI exposes 50+ open-source models from Workers and supports text generation, embeddings, summarization, and other tasks. Text generation is rate-limited to 300 requests/minute by default; paid models have lower per-model limits.
- Evidence: Workers AI overview describes serverless model inference; the limits page gives task and paid-model rate limits.
- URLs:
  - https://developers.cloudflare.com/workers-ai/
  - https://developers.cloudflare.com/workers-ai/platform/limits/
- Source dates: 2026-04-21 and 2026-09-17
- Confidence: high

### 5. Queues are the right boundary for reliable asynchronous agent jobs.

- Claim: Cloudflare Queues provide guaranteed delivery, retries, delays, batching, dead-letter queues, and pull consumers.
- Evidence: The Queues overview lists these capabilities and describes offloading work from a request.
- URL: https://developers.cloudflare.com/queues/
- Source date: last updated 2026-04-21
- Confidence: high

### 6. Durable Objects and D1 provide stateful options for session memory.

- Claim: Durable Objects combine compute with strongly consistent durable storage and now support SQLite storage; D1 is a managed serverless SQL database with SQLite semantics.
- Evidence: Cloudflare's Durable Objects and D1 pages describe these storage models and their Worker integrations.
- URLs:
  - https://developers.cloudflare.com/durable-objects/
  - https://developers.cloudflare.com/d1/
- Source dates: 2026-07-15 and 2026-04-30
- Confidence: high

### 7. Workflows are useful for multi-step agent jobs and human approval.

- Claim: Workflows provide durable multi-step execution, retries, sleep, and waiting for external events or approvals.
- Evidence: The Workflows overview gives an image-processing example that waits for approval and describes durable steps and automatic retries.
- URL: https://developers.cloudflare.com/workflows/
- Source date: last updated 2026-09-18
- Confidence: high

### 8. Vectorize can support retrieval/memory, but it does not execute tools.

- Claim: Vectorize is a vector database for embeddings and semantic search and can be used for RAG or agent context.
- Evidence: Cloudflare describes Vectorize as a globally distributed vector database that works with Workers AI and Workers.
- URL: https://developers.cloudflare.com/vectorize/
- Source date: last updated 2026-04-21
- Confidence: high

## Architecture implications

- A Telegram webhook Worker can acknowledge quickly and enqueue work.
- A direct Workers agent is viable only if the tool surface is small, deterministic, and expressible through HTTP, bindings, KV/D1/R2, or Workers AI.
- Arbitrary shell execution, filesystem-heavy workflows, browser automation, and long-lived local tool processes do not fit the Workers execution model.
- For multi-turn state, use D1, Durable Objects, or an external database; for long-running jobs, use Queues or Workflows rather than `waitUntil()`.

## Free-plan storage and API limits relevant to agent memory

- D1 on Workers Free provides up to 5 GB total storage across databases, with a 500 MB maximum per database, 5 million rows read per day, 100,000 rows written per day, and 50 queries per Worker invocation. It is the best fit for structured conversation state, tool results, indexes, and compact long-term memories.
- SQLite-backed Durable Objects on Workers Free provide up to 5 GB total storage, with a 1 GB practical per-object limit documented in Cloudflare's FAQ. They are the best fit when one chat needs serialized, strongly consistent state and low-latency per-chat coordination.
- Workers KV on Free provides 1 GB storage per account, 100,000 reads per day, and 1,000 writes to different keys per day. It is useful for small caches, configuration, and low-write session metadata, but not for a frequently updated transcript or memory graph.
- R2 on Free includes 10 GB-month storage, 1 million Class A operations, and 10 million Class B operations per month, with free egress. Use it for attachments, exported logs, snapshots, and large artifacts rather than hot conversational state.
- Queues on Free include 10,000 standard operations per day and 24-hour non-configurable message retention. A normal message costs roughly three operations: write, read, and delete. Keep queued payloads small and store large state in D1/R2.
- Workflows on Free include 100,000 requests per day shared with Workers requests, 3,000 steps per day, 1 GB-month storage, and 10 ms CPU per invocation. Use them for durable multi-step jobs, approvals, and scheduled maintenance, not for a high-frequency chat loop.
- Workers Free itself allows 100,000 requests per day, 10 ms CPU per HTTP invocation, 128 MB memory per isolate, 50 subrequests per invocation, five Cron triggers, and 100 Workers per account.

## GitHub repository as memory storage

- A GitHub repository can technically store memory as JSON, JSONL, Markdown, or SQLite files through the Contents API, but it is a poor primary hot store for an interactive agent.
- Authenticated REST requests are limited to 5,000 per hour for a personal access token or GitHub App installation token, while `GITHUB_TOKEN` in Actions is limited to 1,000 requests per hour per repository. Unauthenticated public reads are only 60 per hour.
- Updating a file requires reading its current blob SHA and then issuing a serial `PUT` that creates a commit. Concurrent updates can conflict, and GitHub documents secondary limits on content-generating requests.
- The Contents API fully supports files up to 1 MB; files from 1 MB to 100 MB require raw/object media handling, and files over 100 MB are unsupported through that endpoint.
- GitHub warns that Git is not designed as a backup tool, recommends repositories stay ideally below 1 GB, warns at 50 MiB per file, and blocks regular Git files over 100 MiB.
- Recommended role: use GitHub as an append-only audit log, periodic snapshot, human-readable memory export, or backup target. Use D1 or a SQLite-backed Durable Object as the live memory store.

## Architecture implications

- For a Cloudflare-native prototype, use D1 as the default memory store and a Durable Object per Telegram chat only when serialization or per-chat coordination is needed.
- Use R2 for Telegram media and large artifacts, KV for small low-write caches, and GitHub for periodic exports or audit history.
- If the agent needs shell, browser, filesystem, or long-lived local tools, keep the agent core outside Workers and let Workers remain the Telegram ingress and durable job coordinator.

## Open questions

- The practical throughput of a Telegram bot depends on Telegram rate limits and the chosen model/provider, which were not measured in this research pass.
