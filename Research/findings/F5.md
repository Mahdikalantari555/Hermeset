# F5 — End-to-end reference architectures

Research date/access date: 2026-09-22

## Findings

### 1. The simplest working architecture is a direct Workers bot with an external model API.

- Claim: A Worker can receive Telegram updates, call an LLM provider, and reply with `sendMessage`; public repositories demonstrate this pattern on Cloudflare Workers.
- Evidence: `ChatGPT-Telegram-Workers` is explicitly described as a Telegram ChatGPT bot on Workers with provider configuration, KV, streaming, and a one-click deployment; `telegram-bot-cloudflare` provides a minimal Worker example.
- URLs:
  - https://raw.githubusercontent.com/tbxark/ChatGPT-Telegram-Workers/master/README.md
  - https://raw.githubusercontent.com/cvzi/telegram-bot-cloudflare/main/README.md
- Source date: repositories accessed 2026-09-22
- Confidence: high

### 2. The robust hybrid architecture is Workers ingress plus an external agent host.

- Claim: Workers should receive Telegram webhooks, validate and normalize updates, persist/deduplicate them, and enqueue jobs for an external OpenClaw/Hermes/NanoClaw host; the host executes the agent loop and calls Telegram back for delivery.
- Evidence: OpenClaw's transport design separates durable ingress admission from slow agent processing; Hermes and OpenClaw are host-oriented runtimes; Cloudflare Queues provide reliable delivery and retries.
- URLs:
  - https://raw.githubusercontent.com/openclaw/openclaw/main/docs/channels/telegram/transports.md
  - https://raw.githubusercontent.com/openclaw/openclaw/main/README.md
  - https://raw.githubusercontent.com/NousResearch/hermes-agent/main/README.md
  - https://developers.cloudflare.com/queues/
- Source date: sources accessed 2026-09-22
- Confidence: high

### 3. Durable Objects are appropriate for per-chat/session coordination.

- Claim: A Durable Object per Telegram chat or conversation can own session state, serialize turns, store pending tool calls, and coordinate retries without relying on isolate memory.
- Evidence: Cloudflare describes Durable Objects as stateful serverless objects with unique identities and strongly consistent storage; the platform now supports SQLite-backed Durable Objects.
- URL: https://developers.cloudflare.com/durable-objects/
- Source date: last updated 2026-07-15
- Confidence: high

### 4. Workflows fit multi-step agent jobs and approvals.

- Claim: A Worker can trigger a Workflow for a multi-step task, pause for model/tool steps or human approval, and later deliver the result to Telegram.
- Evidence: Cloudflare Workflows support durable steps, retries, sleep, and waiting for external events or approvals.
- URL: https://developers.cloudflare.com/workflows/
- Source date: last updated 2026-09-18
- Confidence: high

### 5. Streaming Telegram responses are possible but must be designed around Telegram delivery semantics.

- Claim: A direct Worker can stream model output to the HTTP client, but Telegram users receive messages through Bot API calls; practical implementations usually send an initial acknowledgement/typing indicator and then edit or send chunks.
- Evidence: `ChatGPT-Telegram-Workers` lists streaming output as a feature; NanoClaw's architecture notes Telegram streaming via post-and-edit in its channel capability table.
- URLs:
  - https://raw.githubusercontent.com/tbxark/ChatGPT-Telegram-Workers/master/README.md
  - https://raw.githubusercontent.com/nanocoai/nanoclaw/main/docs/architecture.md
- Source date: repositories accessed 2026-09-22
- Confidence: medium-high

### 6. Cloudflare Workers AI is useful for lightweight model stages, not arbitrary agent tools.

- Claim: Workers AI can run embeddings, summarization, classification, or text generation close to the Worker, while shell/browser/filesystem tools remain outside the Worker boundary.
- Evidence: Workers AI exposes model inference; Workers limits and runtime characteristics constrain arbitrary local execution.
- URLs:
  - https://developers.cloudflare.com/workers-ai/
  - https://developers.cloudflare.com/workers/platform/limits/
- Source dates: 2026-04-21 and 2026-09-05
- Confidence: high

## Recommended reference architecture

1. Telegram sends an update to a Workers webhook.
2. The Worker validates the secret, extracts the update ID/chat ID, and writes an idempotency record to D1 or a Durable Object.
3. The Worker enqueues a job to Cloudflare Queues and returns 200 quickly.
4. A consumer Worker or external agent host runs the model/tool loop.
5. The agent host stores session state and tool results durably.
6. The host or a delivery Worker calls `sendMessage`/`editMessageText` and records delivery state.
7. Cron or Workflows handle scheduled jobs, retries, and human approvals.

## Open questions

- Whether to let the external agent host terminate Telegram directly or keep Workers as the only Telegram ingress depends on how much edge deduplication, routing, and durability is required.
- Exact cost and latency require a model/provider benchmark.
