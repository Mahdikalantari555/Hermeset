# F4 — Telegram Bot API integration from Cloudflare Workers

Research date/access date: 2026-09-22

## Findings

### 1. A Telegram bot can be implemented as a small Cloudflare Worker.

- Claim: Public examples deploy Telegram bots on Workers using a bot token, a webhook route, and `sendMessage` calls; one project explicitly describes a single-file, dependency-free Worker deployment.
- Evidence: The `cvzi/telegram-bot-cloudflare` README gives Worker setup steps and a `/registerWebhook` route; `ChatGPT-Telegram-Workers` describes a single-file Workers deployment with streaming output and provider configuration.
- URLs:
  - https://raw.githubusercontent.com/cvzi/telegram-bot-cloudflare/main/README.md
  - https://raw.githubusercontent.com/tbxark/ChatGPT-Telegram-Workers/master/README.md
- Source date: repositories accessed 2026-09-22
- Confidence: high

### 2. Webhook mode is a natural fit for Workers HTTP handlers.

- Claim: A Worker can receive Telegram updates at an HTTPS webhook path, parse the JSON update, call the model/agent, and call `sendMessage`; the Worker URL provides the required public HTTPS ingress.
- Evidence: The minimal Worker example documents registering a webhook and handling a Telegram `Message` object; OpenClaw's Telegram transport documentation describes webhook mode as the alternative when HTTPS ingress is available.
- URLs:
  - https://raw.githubusercontent.com/cvzi/telegram-bot-cloudflare/main/README.md
  - https://raw.githubusercontent.com/openclaw/openclaw/main/docs/channels/telegram/transports.md
- Source date: repositories accessed 2026-09-22
- Confidence: high

### 3. Webhook secret validation and fast acknowledgement are important.

- Claim: Telegram webhook integrations should configure a secret token, validate inbound requests, and avoid holding Telegram's acknowledgement while a slow agent turn runs.
- Evidence: The minimal Worker example tells users to configure `ENV_BOT_SECRET` and references Telegram `setWebhook`; OpenClaw's transport documentation says webhook mode validates the Telegram secret token and commits to a durable queue before returning 200.
- URLs:
  - https://raw.githubusercontent.com/cvzi/telegram-bot-cloudflare/main/README.md
  - https://raw.githubusercontent.com/openclaw/openclaw/main/docs/channels/telegram/transports.md
- Source date: repositories accessed 2026-09-22
- Confidence: high

### 4. Long polling is an alternative, but Workers is usually better as a webhook receiver.

- Claim: OpenClaw uses long polling by default and webhook mode when an HTTPS ingress is available; Workers is naturally suited to the webhook path, while long polling is better implemented by a continuously running host process.
- Evidence: OpenClaw's Telegram transport documentation states that long polling is the default and webhook mode is the alternative for HTTPS ingress.
- URL: https://raw.githubusercontent.com/openclaw/openclaw/main/docs/channels/telegram/transports.md
- Source date: repository content accessed 2026-09-22
- Confidence: high

### 5. Telegram updates should be treated as at-least-once events.

- Claim: A robust integration should deduplicate by Telegram update/message ID and make outbound sends idempotent, because webhook redelivery or a crash after a side effect can repeat an update.
- Evidence: OpenClaw documents durable ingress, bounded replay deduplication, and the possibility of repeated side effects after a crash; this is directly applicable to a custom Workers design.
- URL: https://raw.githubusercontent.com/openclaw/openclaw/main/docs/channels/telegram/transports.md
- Source date: repository content accessed 2026-09-22
- Confidence: high

### 6. Media and rich messages require explicit handling.

- Claim: A simple text bot is easy; photos, documents, voice notes, inline buttons, edits, and file downloads require additional Bot API calls and storage/processing decisions.
- Evidence: OpenClaw's Telegram documentation separates media, rich messages, threads, access control, and events into distinct areas; the minimal Worker example only demonstrates text replies.
- URLs:
  - https://raw.githubusercontent.com/openclaw/openclaw/main/docs/channels/telegram.md
  - https://raw.githubusercontent.com/cvzi/telegram-bot-cloudflare/main/README.md
- Source date: repositories accessed 2026-09-22
- Confidence: medium-high

## Architecture implications

- Use a Worker webhook for low-latency ingress and enqueue the normalized update.
- Store update IDs and delivery state in D1 or a Durable Object.
- Return 200 after durable admission, not after the agent finishes.
- Use a separate consumer/host for long-running model and tool execution.

## Open questions

- Official Telegram Bot API pages were blocked by the research environment's network policy, so exact rate-limit numbers and the latest method-specific limits were not independently fetched in this pass.
- Telegram's official Bot API documentation remains the authoritative source for current method semantics: https://core.telegram.org/bots/api
